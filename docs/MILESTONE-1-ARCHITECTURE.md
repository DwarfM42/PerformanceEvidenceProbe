# Milestone 1 architecture (implementation note)

> This is a concise technical design note. For current user-facing behavior,
> use the root [README](../README.md), the [evidence schema](EVIDENCE-SCHEMA-DRAFT.md),
> and [known limitations](KNOWN-LIMITATIONS.md).

## Ownership and lifetime

`main` owns a run controller.  The Windows controller owns the root process handle and, in launch mode, a Probe Job handle.  The Job has **zero limit flags**; in particular it never sets `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.  Dropping or crashing the Probe therefore cannot be a target-termination mechanism.

A process registry keys every entry by `(pid, process_start_time, boot_identity)` and gives it a monotonically allocated `process_local_id`.  PID is only a lookup hint.  A retained process handle belongs to exactly one live registry entry.  On exit the controller queries final CPU, I/O, and exit-code data; emits its event; releases the handle; and removes it from the retained set.  The `HandleRetention` admission guard is bounded by configuration.  Failed admission emits a degradation event and never invents final values.

## Evidence protocol

The three NDJSON streams are owned by exactly one bounded-queue writer thread. Each record is serialized as one JSON object followed by `\n`, then flushed. A completed run writes the static JSON metadata after the raw streams have been finalized and the summary has been regenerated. This permits a reader to discard exactly one malformed final EOF fragment after a crash. A malformed interior line is an evidence error.

`samples.ndjson` is raw-first: cumulative times, bytes, and operations are preserved; rates are not collector authority.  `process_set_working_set_sum_bytes` is explicitly a process-set sum, not unique physical memory.

## Scheduler

The controller captures a monotonic origin, computes each deadline as `origin + n × 500 ms`, and waits to that absolute target.  It records scheduled time, actual monotonic time, delay, and inter-sample gap.  It neither uses relative-sleep accumulation nor changes Windows timer resolution.

## Summary boundary

`summary.json` is regenerated by a separate reader over persisted NDJSON, not from collector state.  Its serialized struct has a fixed field order and contains no generation timestamp, hostname, PID, or randomness.  This makes identical raw evidence produce byte-identical summary output.

## Fidelity and validity

Launch+Job samples retain both per-process observations and OS Job set accounting.  The summary can derive `job_processes_without_observed_identity` without inventing identities.  Measurement validity is `VALID`, `DEGRADED`, or `INVALID`; target failure is a separate run state.
